# Documentation reconciliation checks

Read during the evidence pass. Use the project's applicable instructions as policy; these are review dimensions, not a replacement schema or a reason to add files.

| Area | What to establish | Evidence and useful edge cases |
| --- | --- | --- |
| References and examples | Paths, links, anchors, commands, flags and environment variable names still resolve. | Read their target or actual CLI definition. Check case sensitivity, renamed files, links from outside the edited area, templates and copied snippets. Treat placeholders as placeholders. Never dereference a symlink outside the authorized scope by accident. |
| Claims and results | Features, defaults, requirements, counts, support and security statements match current behavior. | Distinguish implemented, tested, intended and unavailable. Verify outputs in their stated conditions; qualify dated measurements rather than inventing fresh ones. A test fixture or a passing mock is not live integration evidence. |
| Documentation policy | The right document exists once, in the right place, with the required metadata. | Find stale task notes, duplicate topics, orphaned references and docs hidden by broad ignore rules. Preserve useful decisions and exclusions for generated content. Follow global policy when applicable without copying global instructions or private paths into the repository. |
| Task routes | Each anticipated task reaches its current contract and the check that proves it, through pointers to the one source of each fact. | Start from the audit's observations, the map and the files it imports. A direct route needs nothing; propose a pointer, a section link or a heading only where a link is missing or leads to a copy. Keep a long cohesive reference whole when headings reach its parts, and keep framework and manifest conventions. A historical record, task note, experiment or temporary output is not a contract. A copied fact is a second source that drifts; point at its owner instead. Check each `Start here` line against its destination's imports, exports or headings: it names only what the destination holds, and never a decoy or a folder to avoid. |
| Instruction loading | Each intended host receives consistent project facts and only its applicable adapters. | Trace root and scoped instructions, imports, precedence and host-specific files. Identify contradictions and duplicated rules. Check current official docs or local loader evidence before changing a loading mechanism. Missing access to global instructions remains an explicit gap. |
| Developer setup | A contributor can reach the documented first result in the declared environment. | Compare runtime pins, manifest engines, lockfiles, package manager, shell syntax, relative working directories, check commands and sample configuration. Preserve deliberate platform requirements; do not claim Windows, Unix or device coverage that was not exercised. |
| Host integration | Skill names, discovery paths, manifest sources, hooks and configured commands refer to existing, intended resources. | Keep a per-host matrix of static checks, live discovery, live execution and remaining prerequisites. Identical behavior may require different adapter formats. Do not install hosts, change permissions or activate hooks without authorization. |
| Ignore rules and public exposure | Private files are protected, while needed source, examples and docs remain available to a fresh clone. | Check tracked, staged, untracked and ignored paths. Look for credentials, private keys, local environment files, logs, recordings, screenshots, transcripts, personal paths, registry config and local agent state. Review values only through an available redacting scanner or narrow safe inspection; record locations, never values. A broad ignore can hide required files, and adding a pattern does not untrack an existing secret. |
| Distribution boundaries | Claims about a public repo or package match what would actually be shared. | Inspect allowlists, `.npmignore`, package file lists, archive rules and tracked generated assets when applicable. Review candidate package contents with a non-publishing command only after checking lifecycle scripts and side effects. Git history and remote copies need separate authorization and tools; do not call the current-tree review a history scan. Escalate an exposed credential for owner remediation without rotating it or rewriting history yourself. |
| Removal and maintenance | A removal makes the repository more accurate without discarding unique value. | Confirm retired functionality, surviving replacement content and incoming references. Preserve license and attribution requirements. Keep an obsolete example only if it is intentionally historical and labeled. Avoid speculative CI, new check frameworks, support promises or extra documentation just to satisfy a checklist. |

For a host matrix, use one row per intended host and separate **static references**, **live discovery**, **live execution**, and **gap or evidence**. An unavailable host is `not run`, never `passed`. Reuse existing project evidence when its version and scope still match, and identify it as prior evidence.
